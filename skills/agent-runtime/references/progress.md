# Progress and feedback

Change the concise `intent` whenever the next action changes. Describe the concrete question or test,
not internal IDs alone. A request to run code is not evidence that code succeeded.

Human corrections and verification feedback arrive as identified context. Apply relevant corrections
to subsequent choices; distinguish a delivered correction from evidence of improved performance.
Do not claim weight training or a measured benefit without an actual controlled result.

Use `done` when this branch has reached its conclusion; the runner labels budget exhaustion, failure,
waiting, and cancellation separately. Do not fabricate status to make an incomplete branch look finished.
